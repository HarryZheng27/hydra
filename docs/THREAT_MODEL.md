# Hydra's threat model

This is a plain description of what Hydra tries to protect, who it protects it from, where the boundaries are, the controls that hold those boundaries today, and the risks that are accepted rather than fixed. It's written for someone who has never read Hydra's other docs. Every control below names the file and function it lives in, and the test that proves it — a control with no test is either a gap that got a test while writing this document, or an accepted risk that says so.

This document describes what exists in the code today, not what's planned.

## 1. What Hydra protects, and from whom

### Assets

- **Your repositories and their git metadata.** Source files, history, and the shared `.git` directory (config, hooks, refs) that every worktree of a repository has in common.
- **Your secrets and sign-ins.** SSH keys, cloud credentials, `~/.claude` and `~/.codex` (which hold Claude Code's and Codex's own sign-in), and anything else reachable from your home directory or environment.
- **Hydra's own state and tokens.** `globalStorage` (job records, pack cache, logs), and the per-caller tokens that let a process call Hydra's local endpoint.
- **The user token and its handshake file.** The one Hydra token that is ever written to disk: a `user` token each window mints for scripts and CI jobs that act as you (the groundwork for a `hydra` command), kept in `<globalStorage>/helpers/handshakes/<pid>-<port>.json`. Whoever can read it can create, change and cancel the plans scripts make, read heads and lanes, and stop or resume every agent in that window.
- **The integrity of gate results.** The tests, review and screenshots that decide whether a head's work is accepted — if these can be weakened or spoofed, everything downstream of "the gates passed" is false.
- **Your installed app.** The Hydra executable itself, and the update path that could replace it.

### Adversaries and sources of risk

- **A misbehaving or prompt-injected head or lane.** The main adversary this document is about. A head is an agent Hydra runs unattended (`--permission-mode dontAsk` / `approval never`); a lane is an agent you drive, but its terminal still receives text Hydra assembles on your behalf. Either can be *led astray* by instructions hidden in something it reads, not just by a bug.
- **Content an agent reads.** Repository files, web pages (a role with web access), and pack text (instructions, skills, gate output) can all carry text written to look like an instruction rather than data.
- **Other local processes and other extensions** in the same VS Code / editor process, which could try to open Hydra's local endpoint or read its files. The handshake file is the file most worth reading: a process that reads it can act as you (HSEC-60 to HSEC-63, HR-19).
- **Web pages in a browser**, which could try to call Hydra's loopback endpoint (DNS rebinding, CSRF-style requests).
- **A malicious or changed pack.** A pack can run commands and start MCP servers and give an agent new tools; a third-party pack's author, not Hydra, decides what those do.
- **A tampered update.** Something between "the release is built" and "the update lands on your disk" that swaps the installer or its metadata.

### Out of scope, and why

- **Kernel-level isolation** (containers, VMs, or running heads as a separate Windows user). Hydra's confinement (Section 3) uses Claude Code's own settings and Codex's existing Windows sandbox; it does not attempt OS-level process isolation. This is a stated decision, out of scope.
- **A network firewall for agents.** Heads and lanes that have shell/tool access can reach the network; Hydra does not filter it. Also a stated decision.
- **Another user on the same OS account**, or an administrator of the machine. Hydra's controls assume the person running Hydra is the only one with access to that Windows user profile.
- **A compromised Claude Code or Codex binary**, or a compromised sign-in for either. Hydra treats the CLI it launches as the thing doing the confining (settings files, the sandbox); if the CLI itself is malicious or its binary has been tampered with, Hydra's controls don't hold. Hydra does check the CLI's version range (`src/core/cliVersions.ts`) and self-test its behaviour once per binary (`src/core/cliSelfCheck.ts`), but that is a compatibility check, not a code-signing check.
- **A change to how you sign in to Claude Code or Codex.** Also a stated decision; Hydra never touches provider credentials beyond reading the environment variable names their CLIs already expect.

A second way in: a script or CI job on this machine, running anywhere (not necessarily from this window), presents the **user token** from the window's handshake file. The file sits in Hydra's global storage with an access list that admits you alone; the endpoint checks the calling process isn't inside a head, and the token reaches only the plan tools, reading heads and lanes, and stop/resume — never a head's or a lane's tools. The token lives in the endpoint's memory like every other, so it stops working the moment its window closes, whatever happens to the file.

## 4. Accepted risks

| ID | What can happen | Why it's accepted today | What would fix it |
| --- | --- | --- | --- |
| HR-01 | A Claude head can still read outside its worktree (`~/.ssh`, cloud credentials, etc.) through a script it writes and runs via Bash — for example `npm test` running a script that `cat`s a key, or `node -e 'require("fs").readFileSync(...)'`. The sandbox confines *writes*, not *reads*. | Research (Step 2, R2/R5) found Claude Code's own sandbox unavailable on native Windows, and Codex's read-deny profiles leave a lasting `CodexSandboxUsers:(DENY)(R)` entry that applies machine-wide to every Codex sandbox, breaking other unrelated sessions. Denying reads well enough to matter would need a different sandboxing approach than what's available today. | A read-confining sandbox for Windows Bash (or running heads as a genuinely separate OS principal, which is explicitly out of scope per Section 1). |
| HR-02 | A Codex head has no read limits at all: `workspace-write` restricts writes, not reads, so a Codex head can read anything the launching user's account can read. | Research R4: reads can only be denied through a Codex sandbox profile, whose deny entries are global and lasting on this machine — the cost of confining Codex head reads today is breaking every other Codex sandbox session. | The same fix as HR-01, or a Codex-specific read confinement that doesn't leave a shared, lasting deny entry. |
| HR-03 | Whatever a Claude head's sandboxed Bash can read, it can also send over the network — the sandbox leaves the network on, since heads need it for installs and tests. | Turning the network off would break ordinary head work (`npm install`, hitting a dev server, gate screenshots). | A scoped allowlist for outbound network access from the sandbox, if Codex's sandbox profile ever supports one. |
| HR-04 | Gate commands that run when the sandbox check fails (or on non-Windows) run with Hydra's whole, untrimmed environment and no confinement at all — the same as before Step 2. | The sandbox is Windows- and Codex-specific; there is no equivalent confinement path today for other platforms or for a machine where the sandbox self-test failed. | A sandboxing story for macOS/Linux, and a "refuse gate commands rather than run them unconfined" mode for a failed Windows check. |
| HR-05 | A lane has no read block at all: the 8.3, `\\?\` and UNC spellings of a path Hydra denies still read it, and the lane's deny list only names the worktrees that were open when the lane launched — a worktree opened afterward isn't covered. Lanes' own shells are entirely unconfined (they're meant to work like your terminal). | Decision: "Lanes get light limits... Otherwise they work like your own terminal, with your settings and your full environment." A lane is driven by you, not by an unattended agent, so the bar deliberately isn't the same as a head's. | Extending `blockReadsOutsideWorkingDirectories`-style confinement to lanes would contradict the "acts like your terminal" design goal; if that goal changes, the fix is the same read-block used for heads (HSEC-09), refreshed as worktrees open. |
| HR-06 | Your Claude user settings (`~/.claude/settings.json`) still apply to heads (`--setting-sources user`): an allow rule you've set there could let Edit/Write reach outside the worktree, and your settings' `env` block can change a head's environment. Your settings' hooks no longer run for heads or reviewers, and your plugins, CLAUDE.md and auto memory stay out (HSEC-71). | Heads need *some* user-level configuration (models, provider settings) to behave consistently with your own usage; refusing all user settings would also refuse things you intentionally set. | A narrower settings-source that keeps only the subset heads need, once it's clear which subset that is. |
| HR-07 | A worktree's `.codex/config.toml` can be written by a Claude head, and a Codex review gate or a Codex continuation running in that same worktree may load it if Codex trusts the repository — this hasn't been checked. | Found during Step 2's build; explicitly flagged there as "Not checked yet." | Verify whether a Codex process reading a head-written `.codex/config.toml` can change its own sandbox or approval behaviour, and confine or strip that file if so. |
| HR-08 | Every head's sandboxed commands run as the same Codex sandbox user, so one head's command could in principle signal another's, and `/tmp` inside Git Bash is shared and points at whichever command's TEMP happened to be created first (possibly a deleted one, or another head's). | Codex's Windows sandbox uses one sandbox user machine-wide; per-head OS principals are the kind of isolation this document already puts out of scope (Section 1). | Per-head OS users or containers — out of scope per the plan's own decision. |
| HR-09 | Stopping a sandboxed command can take up to about 5 seconds (the guard polls every 2s and then has to enumerate and kill a process tree), a process that leaves the command's own tree isn't followed, and Hydra's own tree-kill logs "could not confirm process-tree termination" when it meets the sandbox's processes (since `taskkill`/WMI are themselves denied inside the sandbox). This is exercised in `tests/confine.test.ts` only at the level of the guard/wrapper scripts' text (HSEC-16); there's no unit test that actually starts a lingering process tree under the real Codex sandbox and confirms it's gone within 5s, because that needs the real sandbox and CLI, which this document's rules keep out of unit tests. | The guard's own live behaviour was verified once, manually, during Step 2's live checks ("after killing the wrapper's tree, an `npm run dev`-like tree ... is gone within about 5 s"), not by an automated test, and can't be, without the real sandbox. | A repeatable integration-style check with the real Codex sandbox (already partially covered by Step 2's live-check protocol), not a unit test. |
| HR-10 | The desktop update trust value (HSEC-42/43) has no automated test proving it is unreachable from a renderer or extension — that property currently rests on there being no code path that exports it, not on an enforced boundary a test can exercise. | `getHydraUpdateTrust` is a plain module-level function in Electron main; VS Code's own process separation between main and renderer is what actually stops a renderer from calling it directly, and testing that separation is outside a focused unit test's reach (it would mean standing up Electron's IPC boundary). | An IPC-boundary test once the update service (whose install step still isn't built; see HR-14) defines what, if anything, a renderer is allowed to ask about update state. |
| HR-11 (from Packs research R8; narrowed by Step 2) | A head writing the lead folder's `.hydra/gates.json` or `packs.json`, or its shared `.git`, is now refused everywhere Step 2 applies. A Claude head's file tools are denied them (HSEC-09). Its Bash runs in Codex's sandbox, where writes outside the worktree fail: the Step 2 live check had `echo > <lead>/.hydra/…` and `git -C <lead> config` refused. It never has PowerShell, and with no sandbox it has no shell at all. A Codex head's `workspace-write` sandbox with its own TEMP refuses them too (research R4). **What remains:** a lead folder inside `%TEMP%`. Codex's own use can leave a lasting write grant for its sandbox user on `%TEMP%` (seen on this machine), so a sandboxed shell could write a repository kept there. | Repositories rarely live in `%TEMP%`. The gate floor (HSEC-21) and the tamper note still apply, and git settings and hooks are checked (HSEC-30). | Warn when the lead folder is under `%TEMP%`, or check the folder's access list for Codex's sandbox group before starting heads. |
| HR-12 (from [Packs_Plan.md](internal/Packs_Plan.md), section 4) | A pack's MCP server, when it runs in a lane rather than a head, can do whatever the lane's agent can do — the review panel says so, but there's no separate confinement on a pack server beyond what the lane itself has. | A lane is already meant to work like your own terminal (see HR-05); confining a pack's server more tightly than the lane that hosts it would be inconsistent with that design. | None planned; this is the same trust boundary as "a lane is your terminal," made explicit for packs. |
| HR-13 (from [Packs_Plan.md](internal/Packs_Plan.md), section 4, R8) | Skills passed to a head have no `--add-dir`, so a head reads a role's skill files the same way it reads anything else in its pack copy — fine while pack copies are trusted, but it means a skill script (flagged "Agents may run these" in the review panel) runs with exactly the head's own confinement, no less and no more. | Skills are pack content you already reviewed and trusted when turning the pack on; treating them differently from the rest of the pack copy wouldn't add a meaningful boundary. | None planned. |
| HR-14 (from Step 4) | Hydra's installers aren't code-signed, and in-app updates are off, so nothing offers you an update. You install each release by hand, and a swapped download is caught only if you check `SHA256SUMS` or the attestation (HSEC-47). SmartScreen warns on every release. | A code-signing certificate, an update host and the update-signing key are the release owner's to provide (`docs/Releases.md`); the repository can't create them. Installing from inside Hydra also still needs the native helper's install step. | The owner inputs in `docs/Releases.md`, then the native install step, then an upgrade test from one signed release to the next. |
| HR-15 (from Step 4) | The release job's actions (`actions/checkout`, `setup-node`, `download-artifact`, `upload-artifact`, `attest-build-provenance`) are pinned by version tag, not by commit, so a compromised release of one of them could change what a Hydra release publishes or attests. | They're GitHub's own first-party actions, and every other Hydra workflow pins them the same way. | Pin every action by commit SHA, with Dependabot keeping the pins current. |
| HR-16 (from Step 5) | Hydra checks a pinned server's hash against registry.npmjs.org, but `npx` downloads from whatever registry your `.npmrc` names. With another registry configured, npm checks the download against that registry's own record, not the pin. A server with an exact version but no `integrity` pin is checked by version only. | Hydra doesn't read or change your npm settings, and forcing a registry on the command line would break packs behind a company mirror. Exact versions still stop a new release from being picked up silently. | Pass the pin to npm itself, for example through a lockfile-backed install into Hydra's pack cache, so npm refuses a download that differs from it. |
| HR-17 (from Step 5) | The redactor matches patterns, so a secret with no known shape, no secret-looking name beside it and no secret-named environment variable holding it passes through: for example a bare random password in prose. It also doesn't touch a lane's terminal, which is your own. It also masks some values that aren't secret, such as `session_id` in head transcripts. | Only a secret's shape or name can be matched without knowing every secret in advance; masking all long random strings would hide commit SHAs, hashes and IDs people need. | Let a project list more secret names or patterns, or name the environment variables whose values should always be masked. |
| HR-18 (from Part 2, Step C) | In a plan that auto-dispatches to lanes, Hydra types a failed gate's output into the lane **and presses Enter**, so the lane's agent acts on it without you reading it first. A gate command's output can carry instructions written by whatever the command ran. | The output comes from the lane's own worktree and goes back to the same agent, which already controls that worktree, so it gains nothing it didn't have. The text is cleaned as for Send to lane (HSEC-33) and capped at 1,500 characters. Dispatch is opt-in per plan, and turning it off returns to Send to lane, which never presses Enter. | Show the failure in the lane tile and wait for a click, for projects that want review before every retry. |
| HR-19 (from O8a) | A process running as your own account can read the handshake file and act as you in that window (HSEC-60's tools, including Resume Agents after a Stop All, and HSEC-72's `hydra close --force`, which ends every head and lane at once, as Stop All already does, and closes the window). That includes a head's shell where it runs as you: a Codex head, whose reads aren't limited (HR-02), and a Claude head's Bash when it runs without the sandbox. HSEC-63 refuses such a process while it is still a descendant of the head, but one that detaches itself (so the OS no longer links it to the head) passes. A reused PID could make a crashed window's handshake look live until it is matched against the live discovery record; the token itself is dead either way. | The access list is the boundary the plan asks for: it keeps out every other account, including a sandbox's own. A file nothing running as you could read would be unreadable by the script too. A sandboxed Claude head's Bash runs as the sandbox's account, which the access list leaves out, and its file tools are denied Hydra's storage (HSEC-11). | Hand the token to a script only through a check a head can't pass (for example a one-time exchange that requires the caller to reach the window, as the lead check does), or refuse a user-role Resume while any head is running. |
| HR-20 (from HSEC-68) | Any installed extension can run a command, so any extension can show a toast branded Hydra, with its own words and buttons. It can't make the toast do anything: pressing a button only answers that extension's own call. | The notice commands exist so Hydra's own extension can reach the workbench, and the editor has no way to limit a command to one caller. Standard editor notifications carry the same risk under their own look, and an extension can already open any editor or webview it likes. | Pass a per-window secret from the workbench to Hydra's extension only, and require it on `hydra.desktop.notice.show`. |
| HR-21 (from HSEC-71) | Some of your own configuration can still reach a head or reviewer. When Hydra can't make its own Codex home (you sign in with an API key or a keyring, so there's no `auth.json`, or the hard link fails, for example across drives), Codex runs with your home and Hydra's flags: your `config.toml` stays out, but your `AGENTS.md` and skills folder still load; Hydra logs why. Codex also finds skills in `~/.agents/skills` (their listing is off, not the skills). A Claude head with a role that grants `Skill` can also see your own `~/.claude/skills`. If Codex ever writes `auth.json` by replacing the file instead of rewriting it, the link would split, and a refresh in Hydra's home would leave the newer tokens only there. Hydra never re-links over a copy that holds a later sign-in than yours (by `last_refresh` when both files have it, else by file time), since with a rotated refresh token that would sign you out. That launch, and each one after until you sign in again, uses your own home instead, and Hydra logs that sign-in may need refreshing (`codex login`). | Copying `auth.json` would split the sign-in at once; there's no Codex setting that skips the global `AGENTS.md`; Claude Code's switch for skills also removes a role's skills. | Re-check the in-place write on each Codex update (tests/agentHome.test.ts pins the link behaviour; the live check is in HSEC-71); skip user skills once either CLI has a setting for it. |

## 5. How to report a problem

Report a suspected security problem privately, never in a public issue: [SECURITY.md](../SECURITY.md) explains how, through GitHub's private vulnerability reporting on this repository (`Security` tab → `Report a vulnerability`), so it can be assessed before any details are public.
