# Windows user installer

After `desktop:build` and `desktop:smoke`, run `npm.cmd run desktop:installer` on native Windows x64. This packages the verified standalone app using the pinned upstream Inno Setup user-installer task. It produces `.desktop/code-oss/.build/win32-x64/user-setup/HydraSetup.exe`. The bundled module and product version must match the current Hydra manifest, preventing accidentally packaging a stale runtime.

The installer uses Hydra's isolated application/registry identities and logo. Installer versioning follows Hydra's module version; the editor API remains at its upstream version for extension compatibility. The artifact is currently unsigned. It is published as a GitHub pre-release (first: [v0.23.0](https://github.com/ndunl075/hydra/releases/tag/v0.23.0), an unsigned Windows preview); code signing and automatic updates are not configured.

**The name, Hydra IDE.** `desktop/product.json`'s `nameLong` is "Hydra IDE", so shortcuts, the Start Menu folder, the title bar and `vscode.env.appName` say Hydra IDE. Everything an installed copy depends on keeps its old value: `nameShort`, `dataFolderName`, the AppIds, `win32AppUserModelId` (`Hydra.IDE`, so taskbar pins survive), `win32RegValueName`, `win32NameVersion` (the registration's display name, which the upgrade check compares), the install folder and `HydraSetup.exe`. The handover is in `desktop/hydra-shortcuts.iss` and `brandedInstaller` in `scripts/desktop.mjs`:

- **Upgrade:** before installing, the installer notes the Start Menu folder the installed version used. Once the "Hydra IDE" shortcuts exist, it deletes the old `Hydra.lnk` on the desktop, in Quick Launch and in that folder, but only one whose target is this installation's `Hydra.exe`; any other `Hydra.lnk` (the Hydra app's) is left alone. The old folder goes only if it's then empty. `UsePreviousGroup=no` moves upgrades into the new **Hydra IDE** folder.
- **Uninstall:** Inno appends each install's entries to one uninstall log, so an uninstall would also delete every path an earlier version logged, including the old `Hydra.lnk` where the app's shortcut now lives. `UninstallLogMode=overwrite` writes a fresh log at every install, so only the current shortcuts are removed. (`new` keeps the old log and adds a second uninstaller.) A fresh log no longer lists files that only an earlier version installed, and a leftover install folder would make a later install refuse it. So `[UninstallDelete]` also removes the installer's own folders (`resources`, `locales`, `tools`, `policies`) and Electron's top-level runtime files by name or type, never `unins000.*` or the whole folder. The fresh log also doesn't list the install folder after an update, since that install didn't create it, so uninstall removes it at the end if it's empty (`RemoveDir`, which never removes a folder with anything in it). The upgrade test checks that uninstalling after an upgrade leaves no install folder at all.
- **Installer identity:** `HydraSetup.exe` keeps its PE product name "Hydra" (`VersionInfoProductName`), which the signed update helper checks; Inno would otherwise take `nameLong`.

**Create a desktop shortcut** remains unchecked on a fresh install. Inno remembers prior task selections during reinstall. An explicit opt-out removes Hydra's previous desktop shortcut; background updates retain existing shortcuts. The standard visible installer offers launch afterward. Tests suppress launching the app, file associations, and PATH changes.

The Windows desktop CI job generates the installer only after native desktop acceptance. `scripts/desktop-installer-test.ps1` refuses execution outside a disposable GitHub-hosted Windows runner. It checks fresh default-off behavior, opted-in shortcut target, remembered selection on reinstall, explicit opt-out, the "Hydra IDE" Start Menu shortcut, and uninstall cleanup. A stand-in for the Hydra app's desktop `Hydra.lnk` must come through every install and uninstall unchanged. Sentinel files prove Hydra preferences/extensions, VS Code and Cursor preferences, and an unrelated project survive. Existing Hydra registration/shortcut causes refusal rather than replacement. Logs and successful installer artifacts are retained for seven days.

The original lifecycle gate tests same-version reinstalls. The distinct-version upgrade gate in `scripts/desktop-upgrade-test.ps1` passed on [disposable Windows run 35485520776, attempt 2](https://github.com/ndunl075/hydra/actions/runs/35485520776/attempts/2), after the product staging fix in [PR #126](https://github.com/ndunl075/hydra/pull/126). It refuses execution outside disposable GitHub-hosted Windows runners and never tests a developer's installed profile.

`desktop/upgrade-baseline.json` pins the published [v0.23.0 release](https://github.com/ndunl075/hydra/releases/tag/v0.23.0) (`source: "release"`: tag, tagged commit, `HydraSetup.exe` asset and its SHA-256). CI checks the release is published, its tag still points at the recorded commit and GitHub's asset digest matches, then downloads it; the upgrade script re-checks the hash. A release doesn't expire; the older artifact form (a CI run and artifact, with `expiresAt`) still works, exact source head, immutable installer artifact ID/digest and installer SHA-256. CI verifies run/artifact provenance before downloading with read-only Actions access; the script verifies the installer file hash before execution. An expired or mismatched baseline fails the gate rather than selecting an unverified replacement. CI artifacts expire after seven days; explicitly revalidate the baseline when necessary.

The gate requires a strictly newer current Hydra version. It tests separate prior-install/upgrade/uninstall cycles with both selected and unselected desktop shortcuts, verifies remembered selection and shortcut target, and checks product/module/registry version identity. It checks the Hydra IDE handover: after the upgrade the prior release's `Hydra.lnk` shortcuts and "Hydra" Start Menu folder are gone and "Hydra IDE" ones open the same `Hydra.exe`; a stand-in for the app's `Hydra.lnk` on the desktop survives the upgrade; stand-ins planted at both old `Hydra.lnk` paths survive the later uninstall, which must leave nothing in the install folder. Executable and bundled-module bytes must match the exact current CI build. The pinned Inno task adds `target: "user"` to `product.json` before packaging; the gate verifies that this is the only semantic change from the built product and that the installed product matches the staged installer input byte-for-byte. Hashed sentinels cover Hydra settings, a named profile, task metadata, extensions, VS Code/Cursor preferences and an unrelated project. Logs and provenance are uploaded even on failure. Attempt 2 of the linked disposable run passed this automated gate; visible wizard/launch-after-install acceptance and signing remain outstanding.

The commands and task-selection behavior follow the [official Inno Setup command-line documentation](https://jrsoftware.org/ishelp/topic_setupcmdline.htm) and [uninstaller documentation](https://jrsoftware.org/ishelp/topic_uninstcmdline.htm).
Cross-run artifact download inputs follow the [pinned official download-artifact v4 action](https://github.com/actions/download-artifact/blob/v4/action.yml).
